# Tablify — Implementation Guidelines (Phase 0–8)

**Type:** Plan only. No code is in this document.
**Companion docs:** `FEATURES.md` (what), `ROADMAP.md` (order, dependencies, decisions, risks).
**Scope:** All 9 phases and all 49 work items in `ROADMAP.md`.
**Priority order for every decision:** correctness → reliability → efficiency → maintainability.

---

## 0. Rules that apply to every step

### 0.1 Evidence standard (what counts as "done")

- A step is done only when its **Acceptance** criteria pass and the evidence is recorded in `docs/evidence/<step-ID>.md`.
- Each evidence file contains: commit hash, date, tester name, environment (OS, Obsidian version, device if mobile), exact commands run, test counts (passed/failed/skipped), links to logs or screenshots, and any deviations.
- Do not write "fully tested", "bug-free", "100% accurate", or "fast" without a measurement or test that shows it. Use measured wording instead, for example: "passes 412 of 412 unit tests at commit `abc123`; differential test found 0 mismatches in 10,000 random cases."
- If a check cannot be run (for example, no iOS device available), mark it **NOT RUN** with the reason. A NOT RUN check blocks the phase gate until the owner accepts the risk in the decision log.

### 0.2 Test types (codes used below)

| Code | Type | What it proves | Tool |
|------|------|----------------|------|
| T-U | Unit | One function or module behaves as specified | Vitest |
| T-M | Model-based | Real code matches a simple reference model over random operation sequences | Vitest + seeded random generator |
| T-D | Differential | Our implementation matches an independent implementation on the same inputs | Vitest; reference library used in tests only |
| T-F | Fuzz | Malformed input never causes an uncaught exception or data corruption | Vitest + seeded generator, run N ≥ 10,000 |
| T-I | Integration | Plugin works inside a real Obsidian vault (file events, vault API, commands) | Test vault on desktop |
| T-E | End-to-end UI | A user flow works from the UI through to the file on disk | UI automation if available (chosen in P0-02); otherwise T-M |
| T-P | Performance | A measured value meets a PERF target | Benchmark script (§0.4) |
| T-S | Security/privacy | Secrets and forbidden references do not appear where they must not | Grep and runtime checks |
| T-M-DEV | Manual on device | Behavior on a real phone or desktop OS | Scripted test case with recorded result |

### 0.3 Test fixtures (deterministic)

All generated fixtures use a fixed seed, so every run creates the same data.

| Fixture | Rows | Columns | Use |
|---------|------|---------|-----|
| FX-S | 100 | 8 (all types) | Unit and integration tests |
| FX-M | 1,000 | 12 (all types) | Target scale (D7), performance tests, regression |
| FX-L | 10,000 | 12 | Stress only; not a release target |
| FX-CSV-RFC | — | — | RFC 4180 examples plus edge cases (quotes, CRLF, embedded newlines, BOM) |
| FX-XLSX | 5,000 | 10 | Dates, merged cells, formulas with cached values, multiple sheets |
| FX-TABULA | — | — | Dummy `.tabula` files. Used only to prove they are ignored (P0-04, A9) |

Fixtures live in `samples/fixtures/` and are generated by a script that is committed. The generator's output hash is recorded in evidence.

### 0.4 Performance measurement protocol

1. Record the hardware: CPU model, RAM, OS version, Obsidian version, device model (mobile).
2. Close other heavy applications. Use a fresh vault containing only the fixture under test.
3. Run 3 warm-up runs (not counted), then 10 measured runs.
4. Report **median** and **p95**. Include the raw numbers in evidence.
5. A PERF target is met only if the **p95** is within the limit.
6. Targets marked *proposed* in §1 must be confirmed by the owner before they appear in any public claim.

### 0.5 Issue handling

| Severity | Definition | Rule |
|----------|-----------|------|
| S1 | Data loss, corruption, or secret leak | Stop. Fix before any further work. Add a regression test |
| S2 | Crash, wrong result, or a blocked MVP scenario | Fix before the step can be accepted. Add a regression test |
| S3 | Functional defect with a workaround | Fix before the phase gate, or defer with owner sign-off in the decision log |
| S4 | Cosmetic or minor | Backlog |

Issue record format (`docs/issues/ISS-###.md`): ID, phase and step, severity, steps to reproduce, expected and actual result, root cause, fix commit, regression test name, verification evidence, status.

**Rule:** No step in phase N+1 starts while any S1 or S2 issue is open against phase N.

### 0.6 Phase gate (applies to every phase)

A phase gate opens only when all of these are true:

1. Every step in the phase has accepted evidence.
2. `npm run lint`, `npm test`, and `npm run build` pass on the phase's release commit.
3. Phase regression tests pass (all tests from earlier phases still pass).
4. No open S1 or S2 issues. S3 issues are fixed or deferred with sign-off.
5. The phase's assumption and limitation register (listed at the end of each phase) is reviewed and each item is either accepted or resolved.
6. A short gate note in `docs/gates/phase-N.md` records the result, the commit hash, and the open risks.

### 0.7 Performance targets (from ROADMAP, with measurement IDs)

| ID | Target | Scope | Status |
|----|--------|-------|--------|
| PERF-1 | Open a FX-M table, p95 < 1,000 ms desktop; < 2,000 ms mobile | P6-02 | Proposed |
| PERF-2 | Filter or search update on FX-M, p95 < 200 ms | P2-02, P3-08 | Proposed |
| PERF-3 | Save FX-M file, p95 < 300 ms | P1-03 | Proposed |
| PERF-4 | Scroll on FX-M: p95 frame time ≤ 33 ms desktop and mid-range phone | P3-01 | Proposed |
| PERF-5 | Parse 10,000-row CSV < 1,000 ms desktop | P4-01 | From ROADMAP |
| PERF-6 | Import FX-M (1,000 rows) < 2,000 ms desktop | P4-04 | Proposed |
| PERF-7 | Export FX-M < 2,000 ms desktop | P4-05 | Proposed |
| PERF-8 | Heap growth after 10 minutes of scroll and edit on FX-M < 10% | P3-01, P6-02 | Proposed |

## 2. Phase 0 — Foundation and format spec

**Phase objective:** A buildable, lintable, testable plugin skeleton, a written format spec, and proof that `.tabula` is ignored.

**Phase prerequisites:** Node LTS installed; an Obsidian desktop test vault; a mobile test device or the ability to sideload via Obsidian Sync or a dev folder; owner decisions D-O4 (min version) recorded when P0-01 completes.

### P0-01 — Scaffold the plugin

- **Objective:** A plugin that loads, shows in the plugin list, and does nothing harmful.
- **Prerequisites:** Repository created; Node LTS; decision on TypeScript and esbuild (locked by roadmap).
- **Actions:**
  1. Create the repo with `manifest.json` (`id: tablify`, `name: Tablify`, `isDesktopOnly: false`, `version: 0.0.1`).
  2. Add `main.ts` that registers one no-op command.
  3. Add the esbuild config. Output `main.js` in the repo root.
  4. Set `minAppVersion` to the lowest version that supports every API used. Record which API calls drove that choice.
  5. Commit `package-lock.json`.
- **Dependencies:** none.
- **Outputs:** Repo skeleton, manifest, build script, `docs/decisions/min-app-version.md`, evidence file.
- **Verification:**
  - T-U: a test that parses `manifest.json` and asserts `id`, `name`, `isDesktopOnly`, `minAppVersion` are present and correct.
  - T-I: install into the desktop test vault, enable, confirm the command appears. Check the developer console for errors.
  - T-M-DEV: enable on iOS and Android. Record the result.
- **Performance:** Record `main.js` size as the baseline. No target yet. Plugin load time recorded for information only.
- **Acceptance:** Plugin loads on desktop and mobile with no console errors. `minAppVersion` is backed by a written reason. Build reproducible from a clean clone (verified by a second clone and identical `main.js` hash).

### P0-02 — Tooling

- **Objective:** Lint, unit test, and build run with one command each, and failures are visible.
- **Prerequisites:** P0-01.
- **Actions:**
  1. Configure ESLint with the Obsidian-recommended rules (use the official sample plugin's config as the reference).
  2. Configure Vitest with coverage output.
  3. Add npm scripts: `lint`, `test`, `test:coverage`, `build`, `check` (runs all).
  4. Decide and record the UI test approach for G-L1 (automated runner, or manual scripts with a template).
  5. Add a CI workflow (or a local script) that runs `check`.
- **Dependencies:** P0-01.
- **Outputs:** config files, `docs/testing/approach.md`, CI file.
- **Verification:**
  - Clean clone: `npm ci && npm run check` passes.
  - Negative test: add an intentional lint violation and a failing unit test on a branch. Both must fail the check. Revert and record.
- **Performance:** `npm run check` on a clean clone completes in under 5 minutes on the reference machine (proposed).
- **Acceptance:** Clean clone passes `check`. Negative test proves the check fails when it should. UI test approach documented.

### P0-03 — Format spec v1

- **Objective:** A written, machine-checkable definition of `.tablify` v1.
- **Prerequisites:** Decisions D2, R-D8, R-D9, R-D10 in `ROADMAP.md`.
- **Actions:**
  1. Write `FORMAT_SPEC.md`. Cover: file encoding (UTF-8), line endings (LF), key order, indentation (2 spaces), trailing newline, every key, types, required vs optional, `formatVersion` rule, unknown-key rule, reserved `sync` and `syncLink` keys, and the statement that `.tabula` is not read.
  2. Write `tablify.schema.json` (JSON Schema draft 2020-12).
  3. Create samples in `samples/v1/`: `empty.tablify`, `typical.tablify` (generated from FX-S), `edge.tablify` (unicode, escaped quotes, newline in long text, empty values, unknown key, `sync: null`), and invalid samples in `samples/invalid/` (wrong type, missing `formatVersion`, duplicate field ID, row referencing unknown field ID).
  4. Ask a second reviewer to check the spec against the roadmap §7 contract.
- **Dependencies:** none (can start in parallel with P0-01).
- **Outputs:** `FORMAT_SPEC.md`, schema, samples, review record.
- **Verification:**
  - T-U: a schema validator (Ajv or equivalent) accepts every file in `samples/v1/` and rejects every file in `samples/invalid/` for the expected reason.
  - Checklist: every field in roadmap §7 appears in the spec. Count and list the items, record the result.
  - Review: reviewer sign-off recorded with the spec commit hash.
- **Performance:** N/A.
- **Acceptance:** All valid samples pass; all invalid samples fail with the expected error; reviewer sign-off recorded; spec states that `.tabula` files are not read.

### P0-04 — Extension guard

- **Objective:** The plugin handles only `.tablify`.
- **Prerequisites:** P0-01.
- **Actions:**
  1. Register only the `tablify` extension wherever the plugin declares file types.
  2. Confirm no import filter, file menu, or migration code references `.tabula`.
  3. Add a repository check that fails the build if `src/` contains the string `tabula` (case-insensitive). Documentation may mention it.
- **Dependencies:** P0-01.
- **Outputs:** Guard code, repo check script, test.
- **Verification:**
  - T-U: the registered extension list equals `["tablify"]`.
  - T-S: `grep -ri tabula src/` returns zero matches. Run in CI.
  - T-I: vault containing `FX-TABULA` files. Confirm the plugin does not open them, does not list them in import, and shows no migration prompt. This is scenario A9.
- **Performance:** N/A.
- **Acceptance:** All three checks pass. Results recorded.

### Phase 0 gate and assumption register

- **Gate:** P0-01 through P0-04 accepted. `check` green. Gate note `docs/gates/phase-0.md`.
- **Assumptions and limitations:**
  - The spec is a v1 contract. Changes after release require a `formatVersion` bump (R11).
  - Obsidian's file-type registration behavior is assumed to match the documentation of the tested version. Verified by T-I.

## 3. Phase 1 — Data core

**Phase objective:** A pure, tested data model for fields, rows, validation, undo, select options, and file read/write.

**Phase prerequisites:** Phase 0 gate passed. Fixtures FX-S and FX-M generated and committed.

### P1-01 — Field type registry

- **Objective:** Each of the 19 field types has one implementation for validate, parse, format, default, and read-only status.
- **Prerequisites:** P0-03 (spec defines the types).
- **Actions:**
  1. Define a `FieldType` interface: `validate(value)`, `parse(input: string)`, `format(value)`, `defaultValue()`, `readOnly: boolean`.
  2. Implement user types: text, long text, number, currency, percent, duration, rating, checkbox, date, date & time, URL, email, phone.
  3. Implement select types: single select, multi select (reference options by option ID).
  4. Implement attachment (vault-relative path string), auto number (read-only), created time and modified time (read-only, ISO 8601 UTC).
  5. Register all types in one registry. Unknown type names in a file produce an error, never a silent default.
- **Dependencies:** P0-03.
- **Outputs:** `src/model/fieldTypes/*`, registry, tests.
- **Verification:**
  - T-U: table-driven tests per type with valid, invalid, and empty values (at least 5 cases each).
  - T-M: for each type, `parse(format(v))` equals `v` for 1,000 random valid values from seeded generators.
  - Edge cases tested: currency rounding (store as integer minor units, state the unit in the spec), duration formats, leap-day dates, URLs with unicode, phone numbers with leading `+`.
  - Coverage of the registry module reported. Target: ≥ 95% line coverage (proposed). Report the actual value.
- **Performance:** Validating 10,000 values across all types < 50 ms desktop (proposed).
- **Acceptance:** All tests pass. Every registered type has a test. Unknown types rejected with a clear error.

### P1-02 — Row store

- **Objective:** A correct in-memory table with stable IDs, timestamps, revisions, and auto numbers.
- **Prerequisites:** P1-01.
- **Actions:**
  1. Store rows in a map keyed by row ID, plus an ordered list for display order.
  2. Generate row IDs with at least 80 bits of randomness, prefixed `row_` (G-A6).
  3. Keep an auto-number counter in table metadata. Never decrement it or reuse numbers.
  4. On each change: increment `rev` by exactly 1 and set `updatedAt` to UTC now.
  5. Expose create, read, update, delete, and reorder operations. Each returns the changed row and never mutates input objects.
- **Dependencies:** P1-01.
- **Outputs:** `src/model/tableStore.ts`, tests.
- **Verification:**
  - T-U: each operation's contract, including input immutability.
  - T-U: 10,000 generated IDs are unique. Record the count and result.
  - T-M: random sequence of 10,000 operations applied to both the store and a simple array-based reference model. Results must match after every operation (check on a sample every 100 steps and at the end).
  - T-U: auto number not reused after delete.
- **Performance:** Create 1,000 rows < 100 ms. Single update < 1 ms (proposed).
- **Acceptance:** Model test matches for all operations. ID uniqueness holds. Auto number never reused.

### P1-03 — Serializer and parser

- **Objective:** `.tablify` files read and written with no data change on a round trip, and invalid files are never overwritten.
- **Prerequisites:** P0-03, P1-02.
- **Actions:**
  1. Serializer: keys in the order defined by the spec, 2-space indent, LF, trailing newline, deterministic output.
  2. Parser: validate against the schema from P0-03 and report the first error with line and column.
  3. Preserve unknown keys on read and write them back in place.
  4. Check `formatVersion` before anything else. Unknown major version → error, no write.
  5. Write path: serialize to a string first. Only write if serialization and validation succeed. Use atomic replace where the platform supports it; otherwise write a temp file and rename.
- **Dependencies:** P0-03, P1-02.
- **Outputs:** `src/format/serialize.ts`, `src/format/parse.ts`, tests.
- **Verification:**
  - T-U: each sample in `samples/v1/` round-trips byte-identical.
  - T-U: each invalid sample returns the expected error with a line and column.
  - T-F: 10,000 seeded random mutations of a valid file. Parser must return either a valid model or an error, never throw. Record the count.
  - T-I: for an invalid file, the write path is never called (mock the vault and assert zero writes).
- **Performance:** PERF-3 save FX-M < 300 ms p95. Parse FX-M < 200 ms p95 (proposed).
- **Acceptance:** Round trips identical. Fuzz: zero uncaught exceptions. Invalid files untouched in T-I.

### P1-04 — Validation engine

- **Objective:** Rules are checked consistently, with no crash on bad rule config or pathological input.
- **Prerequisites:** P1-01.
- **Actions:**
  1. Rules: required, unique, min, max, regex.
  2. Unique: compare trimmed values, case-sensitive by default (document this as an assumption).
  3. Regex: compile once when the rule is set; reject an invalid pattern at config time.
  4. Limit regex input length to 10,000 characters and document that cap, to avoid catastrophic backtracking.
  5. Validation returns a list of violations with row ID, field ID, and rule name. It does not modify data.
- **Dependencies:** P1-01.
- **Outputs:** `src/model/validation.ts`, tests.
- **Verification:**
  - T-U: each rule with a positive and negative case.
  - T-U: invalid regex config rejected.
  - T-P: a known ReDoS-style pattern and input (for example `(a+)+$` with 30 `a`s then `b`) is either rejected at config time or returns in under 100 ms.
  - T-M: random tables validated incrementally vs. full recompute. Results must be identical.
- **Performance:** Full validation of FX-M < 50 ms (proposed).
- **Acceptance:** All rule tests pass. Regex safety test passes. Incremental and full results match.

### P1-05 — Undo and redo

- **Objective:** Local edits can be undone and redone in order.
- **Prerequisites:** P1-02.
- **Actions:**
  1. Each command stores its `do` and `undo` data (not full table snapshots).
  2. Coalesce consecutive edits to the same cell within 1 second into one command (assumption, document it).
  3. Stack limit 100. When full, drop the oldest command.
  4. A new command after an undo clears the redo stack.
  5. Pull and push are not commands (R-D14). Provide a `clear()` used after sync.
- **Dependencies:** P1-02.
- **Outputs:** `src/model/commands.ts`, tests.
- **Verification:**
  - T-M: 1,000 seeded random sequences of commands. After undoing all, the state equals the initial snapshot. After redoing all, the state equals the state before undo.
  - T-U: redo cleared after a new command; limit of 100 enforced; coalescing rule tested with fake timers.
- **Performance:** Apply and undo one command on FX-M < 16 ms (proposed).
- **Acceptance:** 1,000 sequences pass. All unit cases pass.

### P1-06 — Select options

- **Objective:** Options are created, renamed, reordered, and deleted with correct references.
- **Prerequisites:** P1-01.
- **Actions:**
  1. Option has a stable ID, a display name, and a color from a fixed palette.
  2. Create-on-type matches existing options by trimmed, case-insensitive name. If none matches, create one.
  3. Rename changes the name only; the ID stays.
  4. Delete clears the option from all cells that use it (R-D12). Implement as one undoable command.
- **Dependencies:** P1-01, P1-05 (delete must be undoable).
- **Outputs:** `src/model/selectOptions.ts`, tests.
- **Verification:**
  - T-U: create-on-type with same name in different case returns the existing option.
  - T-U: rename keeps references valid.
  - T-M: delete then undo restores every affected cell.
- **Performance:** N/A.
- **Acceptance:** All tests pass. Delete-undo round trip exact.

### Phase 1 gate and assumption register

- **Gate:** P1-01 through P1-06 accepted. Regression: all Phase 0 tests pass. Gate note `docs/gates/phase-1.md`.
- **Assumptions and limitations:**
  - Currency is stored as integer minor units. Currency code and rounding rules must be in the spec (update P0-03 if not).
  - Unique checks are case-sensitive by default.
  - Coalescing window of 1 second is a default, not measured from users.
  - No formula or link types exist yet.

## 4. Phase 2 — Query and view state

**Phase objective:** A query language that is parsed once, evaluated correctly, and stored per view.

**Phase prerequisites:** Phase 1 gate passed.

### P2-01 — Query parser

- **Objective:** Parse the grammar in `FEATURES.md` §2.6 into an AST, with clear errors.
- **Prerequisites:** none in code. The grammar is in `FEATURES.md`.
- **Actions:**
  1. Write the grammar in `docs/query-grammar.md`, including tokenization, quoting, and whitespace rules.
  2. Implement tokenizer and parser. Pure module, no Obsidian imports.
  3. Errors include position (character offset) and a message.
  4. Document ambiguous cases, for example `field:a,b` for text (contains any) vs. multi-select (is any of). Decide and record.
- **Dependencies:** none.
- **Outputs:** `src/query/parse.ts`, grammar doc, tests.
- **Verification:**
  - T-U: at least 30 cases covering each operator row in the table, quoted names, case-insensitive names, empty value, and error cases.
  - T-F: 10,000 seeded random strings. No uncaught exception; every error has a valid position.
  - T-U: print-then-parse round trip gives an equal AST.
- **Performance:** Parse a 1 KB query < 1 ms (proposed).
- **Acceptance:** All tests pass. Fuzz clean. Ambiguous cases documented.

### P2-02 — Filter engine

- **Objective:** A parsed query returns the same rows as a simple reference implementation.
- **Prerequisites:** P2-01, P1-02.
- **Actions:**
  1. Compile each AST term into a predicate using the field type from the registry.
  2. Type mismatch (for example `>n` on a text field) returns a query error, not an empty result.
  3. The builder UI emits a query string through the printer from P2-01, so builder and text query use the same path.
- **Dependencies:** P2-01, P1-02.
- **Outputs:** `src/query/evaluate.ts`, tests, reference implementation in test code only.
- **Verification:**
  - T-D: naive reference evaluator (direct loop over rows) vs. compiled evaluator. 10,000 random queries over FX-M. Zero mismatches required.
  - T-U: 30 hand-written cases with expected row IDs.
  - T-U: type mismatch produces an error.
- **Performance:** PERF-2: filter FX-M < 200 ms p95. Record FX-L for information only.
- **Acceptance:** Zero differential mismatches. Hand cases pass. PERF-2 met on the recorded hardware.

### P2-03 — View state

- **Objective:** View settings save and reload exactly, and never crash when a referenced field no longer exists.
- **Prerequisites:** P1-03.
- **Actions:**
  1. Define the view object: sort list, group field, hidden field IDs, column order and widths, frozen column count, row height.
  2. Validate on load: unknown field IDs are ignored with a warning recorded in the view, not an error.
  3. Reject hiding the primary field (R-D13).
- **Dependencies:** P1-03.
- **Outputs:** `src/model/view.ts`, tests.
- **Verification:**
  - T-U: each setting save and reload.
  - T-U: view referencing a deleted field loads without error and the warning is recorded.
  - T-I: change settings in a real vault, restart Obsidian, confirm settings restored.
- **Performance:** N/A.
- **Acceptance:** All tests pass. Restart test passes and is recorded.

### Phase 2 gate and assumption register

- **Gate:** P2-01 through P2-03 accepted. Gate note `docs/gates/phase-2.md`.
- **Assumptions and limitations:**
  - The grammar covers only the operators in `FEATURES.md`. No OR, parentheses, or NOT across fields in MVP.
  - Date comparisons use UTC unless the spec says otherwise.

## 5. Phase 3 — Grid UI

**Phase objective:** A grid that is responsive on FX-M, edits data through commands, and works with keyboard and touch.

**Phase prerequisites:** Phase 2 gate passed. UI test approach from P0-02 selected.

### P3-01 — Grid shell with virtual rows

- **Objective:** Render only visible rows, with stable scrolling and no growth in DOM size.
- **Prerequisites:** P1-02.
- **Actions:**
  1. Fixed row height per row-height setting; compute visible range from scroll position.
  2. Recycle row elements. Overscan of a small number of rows (document the number).
  3. Column virtualization is optional. Decide and record. If not implemented, document the column limit that stays smooth (measure).
  4. Support touch scrolling on mobile without blocking the page.
- **Dependencies:** P1-02.
- **Outputs:** `src/views/grid/*`, tests, benchmark script.
- **Verification:**
  - T-I: count DOM row elements on FX-M while scrolling. Must stay at visible rows plus overscan.
  - T-P: PERF-4 frame time during a scripted scroll on FX-M.
  - T-P: PERF-8 heap after 10 minutes of scroll and edit cycles.
  - T-M-DEV: scroll on a mid-range phone; record.
- **Performance:** PERF-4 and PERF-8.
- **Acceptance:** DOM count bounded. PERF-4 and PERF-8 met on recorded hardware. Device scroll recorded.

### P3-02 — Cell editors

- **Objective:** Each field type can be edited, validated, and saved through a command.
- **Prerequisites:** P3-01, P1-01.
- **Actions:**
  1. One editor per type. Enter commits, Escape cancels, blur commits.
  2. Every commit goes through a P1-05 command.
  3. Read-only types show no editor.
  4. Invalid input: keep editor open, show the error, do not write.
- **Dependencies:** P3-01, P1-01, P1-05.
- **Outputs:** `src/views/grid/editors/*`.
- **Verification:**
  - T-E: for each type, edit a cell, press Enter, confirm the value in the file on disk.
  - T-E: Escape leaves the file unchanged.
  - T-E: invalid input does not change the file.
  - T-U: each editor's commit calls the command path (spy test).
- **Performance:** Edit commit < 50 ms on FX-M (proposed).
- **Acceptance:** All T-E cases pass for every type. Evidence includes before and after file contents.

### P3-03 — Select dropdown and option manager

- **Objective:** Users choose or create options without leaving the grid, and manage them in one place.
- **Prerequisites:** P3-02, P1-06.
- **Actions:**
  1. Searchable dropdown. Typing an unknown name offers "Create".
  2. Option manager dialog: rename, recolor, reorder, delete with confirmation.
  3. Test input with IME composition (for example Japanese or Chinese input) and document the result.
- **Dependencies:** P3-02, P1-06.
- **Outputs:** `src/views/grid/select/*`.
- **Verification:**
  - T-E: create-on-type creates exactly one option when typed twice with different case.

## 11. Cross-phase rules

1. **Regression:** Every phase gate re-runs the test suites of all earlier phases.
2. **Fixture stability:** FX-S and FX-M hashes do not change unless the spec changes. A change requires a note in the decision log.
3. **Format changes:** Any change to the on-disk format after P0-03 is reviewed against `FORMAT_SPEC.md` and needs a `formatVersion` decision.
4. **Scope:** Anything in `ROADMAP.md` §2 non-goals requires a decision log entry before work starts.
5. **Evidence retention:** Evidence files stay in the repo under `docs/evidence/` and `docs/gates/`.
6. **Claims:** Public text (README, release notes, store listing) may only state a result that appears in an evidence file, with the same wording and conditions.
