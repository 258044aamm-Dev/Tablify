# P7-02 — Airtable client

- **Linear:** SAD-51
- **Phase:** P7 — Embeds and Airtable sync (v1.1) (see `spec/phases/P7.md`)
- **Scope:** v1.1
- **Read first:** `spec/glossary.md`, `spec/guidelines.md` §0 (rules) and §1 (assumptions), `spec/roadmap.md` §3 (decisions)
- **Source:** copied unchanged from `spec/guidelines.md` (section for P7-02)

- **Objective:** Reliable API calls with pagination, rate limits, and clear errors.
- **Prerequisites:** none in code. Airtable docs checked.
- **Actions:**
  1. Use `requestUrl` for every call.
  2. Pagination: follow offsets until complete.
  3. Rate limits: queue requests per base. Keep below the documented limit (record the limit from the docs version checked). On 429, back off and retry with a capped number of attempts.
  4. Map HTTP errors to typed errors with user-facing messages. Never include the token in messages.
- **Dependencies:** none.
- **Outputs:** `src/sync/airtableClient.ts`, tests, mock server.
- **Verification:**
  - T-U with mock server: 429 with retry; 5xx; 401 bad token; 403 missing scope; pagination across 3 pages.
  - T-I (live, test base): list bases and tables; read 2,500-record test table; verify count and a sample of values against a file created by the test script.
  - T-S: token never appears in error messages or logs (grep test on captured logs).
- **Performance:** 2,500 records pulled in a time recorded for information. No fixed target (network-dependent).
- **Acceptance:** Mock and live tests pass. Rate limiter never exceeds the recorded limit in the test log.
