# SAD-303 — Phone country support, and import types that survive a round-trip

**Issue:** [SAD-303](https://linear.app/sad-mod/issue/SAD-303/please-address-the-following-two-issues) (Improvement + Feature, P2)
**Plan:** [`docs/plans/sad-303-phone-country-and-import-types-plan.md`](../plans/sad-303-phone-country-and-import-types-plan.md)
**Status:** delivered in five commits; **In Review**

## What the owner asked for

1. A Phone field with a country code: a selector with a sensible default, a searchable list, a
   modern look, and correct handling when **storing, displaying and exporting**.
2. Import and export must keep field types: phone numbers as Phone fields, email addresses as
   Email fields, everything else as whatever it really is — consistent through import and export.

## The shape of the answer

| Concern | Decision |
|---|---|
| Stored form | **E.164** (`+8801712345678`) in the cell — a string, so every existing reader keeps working |
| Per-field default | Optional `phoneCountry` (ISO alpha-2) in the field; absent = the reader's region, then US |
| Display | Derived, not stored: `formatPhoneDisplay()` in the cell only. `phoneType.format()` is untouched, so grouping, conversion and export are unchanged |
| Country list | 245 regions from `libphonenumber-js/min` 1.13.15, names from `Intl.DisplayNames` (ISO fallback), searchable by name, ISO, calling code and ~30 aliases |
| Invalid values | Kept exactly as typed. `validate()` and `format()` are untouched; only a certified-valid number is rewritten |
| Import | New `email` / `url` / `phone` inference rules, ordered so no existing column changes type |

### Bundle

|---|---|---|---|
| `main.js` raw | 851,625 B | 1,141,928 B | **+34.1 %** |
| `main.js` gzip | 201,903 B | 259,148 B (measured with `gzip -c main.js`) | +28.3 % |
| `styles.css` | — | 326,115 B | phone rows, panel, media queries |

The size is `libphonenumber-js/min` (its metadata is the 245-country validation and formatting
data). It is the price of correct E.164 conversion for every country rather than a hand-written
table that drifts. Nothing on a hot path: the country list is built once and memoised per locale;
5,000 parses take 69 ms; inference p95 on 5,000 × 10 is ~20 ms (limit 500 ms).

### P4-03 accuracy, re-measured

`docs/reports/p4-03-accuracy.md` is regenerated from the relabelled set:

- labelled set: **34 columns** × 100 values (was 30);
- strict accuracy **76.5 % (26/34)**, up from 73.3 % (22/30);
- **email, url and phone: precision 100 %, recall 100 %**;
- the **proposed 90 % threshold is still not met** — the noisy numeric/date/checkbox columns from
  the original set account for every remaining miss, and changing the rules to chase them would
  lose data. The report says so and keeps the owner decision open.

## What was deliberately not touched

`createEditCellCommand`, the store, the command stack, CSV/Markdown/XLSX writers, `cellText`,
search/sort/query/grouping, validation rules, sync value mapping, `formatVersion` — zero diff.
Existing `.tablify` files are not rewritten on open; the new key is preserved by older readers.

## Manual checks worth repeating on a device

1. **Default country** — Add Field → Phone → *Default country*: search `880`, `bangla`, `bd`,
   `uk`; pick Bangladesh, save, reopen the field, confirm it is remembered; change the type to
   Text and confirm the key disappears from the saved file.
2. **National entry** — type `01712345678` in a BD-defaulted cell: the field shows `01712-345678`,
   the preview `+880 1712 345678`, and the saved value is `+8801712345678`.
3. **Paste international** — paste `+1 415 555 2671` into a BD-defaulted cell: the country flips to
   US and the number is stored `+14155552671`.
4. **Invalid input** — type `12345`: the preview says it is not valid for the country, and the
   saved value is exactly `12345`.
5. **No write on dismiss** — open a populated cell, press Escape: no undo entry, no file write.
6. **Round-trip** — export a table with email, URL and phone columns to CSV and XLSX, import each
   again: the columns come back as Email, URL and Phone, with the same values.
7. **Touch** — on a phone/tablet: rows are 44 px, the card is 352 px wide and flips above the cell.

## Known limitations (stated, not hidden)

- A spreadsheet that coerces a number to scientific notation (`8.8E+12`) has already lost digits;
  Tablify cannot reconstruct them, and the column stays Number.
- Email detection is shape-only (RFC-lite): `a@b.c` is accepted, as the field type does.
- A national phone column needs either a phone-like header or a `+`; a bare `(555) 123-4567` under
  `Contact` stays text on purpose.
- Country flags are drawn as two-letter monograms: Windows' Segoe UI Emoji ships no flag glyphs.
- `phoneCountry: "ZZ"` in a hand-edited file is accepted by the parser (so the file still opens)
  and ignored by the UI, which falls back to the reader's region.
