# SAD-100 — Default Column Freeze Behavior

**Issue:** [SAD-100](https://linear.app/sad-mod/issue/SAD-100/default-column-freeze-behavior) (Improvement, P1)
**Plan:** [`docs/plans/sad-98-sad-100-fix-plan.md`](../plans/sad-98-sad-100-fix-plan.md) §Step 3
**Status:** complete

## What the owner asked for

Disable column freezing by default in mobile view and enable it by default in desktop view,
applied consistently from the **current viewport, not the device type**.

## Owner decisions (confirmed interactively before planning)

1. **Viewport default, explicit choice wins** — the viewport decides until the user touches
   **Options → Freeze primary column** or the header **Freeze column**; after that the choice is
   saved in the file and applies at every size.
2. **Mobile view = table pane width ≤ 639px** (the existing phone-layout breakpoint), measured on
   the table pane — never `Platform.isMobile`.

## What was there

`createDefaultView` hard-coded `frozenColumns: 1` — every new table froze the primary column on
every device — and every load/save forced the key to a number (`normalizeView` coerced missing to
`0`), so no file could express "follow the viewport".

## What changed

**File state — optional view key `freezeMode: 'viewport' | 'fixed'`** (the `search`/`query`/
`collapsedGroups` precedent: conditional copy in `cloneView`, appended last in `VIEW_KEYS`,
declared optional in `tablify.schema.json`, validated in `normalizeView`). **No `formatVersion`
change.** Interpretation (`freezeModeOf`):

| Stored state | Meaning |
|---|---|
| `freezeMode: 'viewport'` | mobile pane (≤639px) renders 0 frozen; wider renders the stored count (default 1) |
| `freezeMode: 'fixed'` | the stored count applies at every width |
| absent + `frozenColumns === 1` | legacy hard default → behaves as `'viewport'` |
| absent + `frozenColumns` 0 / ≥2 | legacy deliberate value → behaves as `'fixed'` |

**Runtime — `effectiveFrozenColumns(view, paneWidth)`** (`src/model/view.ts`, breakpoint
`MOBILE_PANE_MAX_WIDTH = 639` matching `styles.css`):

- `GridView.measure` renders the **effective** count from the live pane width
  (`currentPaneWidth` = the grid shell's measured width, falling back to the host-provided
  `viewportWidth` before first layout). The existing ResizeObserver → `refreshGeometry` →
  `measure` chain re-applies it on resize — crossing 639px flips the freeze live. An
  `onPaneWidthChange` callback syncs the toolbar's switch to the new effective state.
- The **Options switch** shows the effective state (projected in `tableView.toolbarState`), so
  its toggle inverts exactly what the user sees. Every write path — the switch
  (`setFrozenColumns`) and the header **Freeze column** — stamps `freezeMode: 'fixed'`, so the
  explicit choice sticks at every size.
- `createDefaultView` writes `frozenColumns: 1` + `freezeMode: 'viewport'`. An older plugin build
  that drops the unknown key falls back to its old always-frozen behaviour — the safe direction.

## Semantics notes (as-built refinements of the plan)

- **`viewport` + stored N** means "N on desktop-width, suppressed on mobile" — not "ignore N".
  This keeps every existing spread-override path (`{ ...createDefaultView(f), frozenColumns: N }`)
  rendering exactly as before on desktop widths; only the mobile suppression is new.
- Legacy `frozenColumns: 1` is reinterpreted as viewport-auto: wide panes render bit-identically
  to before, narrow panes unfreeze (the point of the issue). A user who deliberately froze on
  mobile recovers it with one switch tap (`freezeMode: 'fixed'` is then saved).
- The breakpoint basis is the table pane's measured grid width (split panes behave per pane).
  The phone *toolbar styling* still keys off window width (CSS media) — cosmetic, unchanged.
