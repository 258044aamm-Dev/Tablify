## Objective

Every text/background pair on Core, 720 XP-12 Pro, and FX-M in light and dark themes meets WCAG 2.1 AA (4.5:1 body). Accents that fail AA are documented as non-text.

## Deliverables

- `src/ui/theme/contrast.ts` — `hexToRgb`, `srgbToLinear`, `luminance(hex)`, `contrastRatio(a,b)`, `meetsAA(ratio, large?)` (WCAG formula `(L1+0.05)/(L2+0.05)`)
- `src/ui/theme/tokens.ts` — already P3-09 (palette: dark #141413, light #faf9f5, midGray #b0aea5, lightGray #e8e6dc, accentOrange #d97757, accentBlue #6a9bcc, accentGreen #788c5d; lightTheme bg #faf9f5/text #141413, darkTheme bg #141413/text #faf9f5)
- `scripts/check-contrast.mjs` — Node runner that prints 12 pairs with ratio, AA/large pass, and intended use; exits 0 only if body text pairs pass AA
- `tests/ui/contrast.test.ts` — 6 tests: light text/bg AA, dark text/bg AA, orange on light fails AA but passes on dark, blue on light fails, green on light fails AA but passes large (3:1), muted/border on light fails AA & <3:1

Interpretation per `spec/branding.md` §5 rule:

- Body text **PASSES AA 4.5:1 on every surface it is actually painted on** — base background (17.50:1), striped rows (light 14.73:1, dark 13.81:1) and the header / subtle surface (light 14.73:1, dark 12.19:1).
- Accents orange (#d97757), blue (#6a9bcc), green (#788c5d) **FAIL AA on light** (2.96, 2.78, 3.49) — so they are **not used for body text on light**; they are used for selection, focus ring, and non-text UI. On dark they PASS AA, so they are safe as text on dark.
- Muted (`#b0aea5`) and border **FAIL AA and <3:1 on light** (2.11) — documented as secondary/border, not body text.
- This matches the spec line: “Check the orange and green accents as text on light backgrounds before use; use them for non-text elements if they fail.” — done; they are non-text on light.

> **Correction (SAD-69 D).** The original version of this file reported the dark-theme stripe as
> `lightGray on dark (stripe): #e8e6dc on #141413 → 14.73:1`. That pair was never what the code
> used: `darkTheme.bgStripe` was `palette.midGray` (`#b0aea5`), not `lightGray`. The dark stripe
> therefore put body text (`#faf9f5`) at **2.11:1 — a hard AA failure on every other row**.
>
> The error was a direction-of-comparison slip. Muted-on-dark measures 8.29:1, which reads as a
> pass and was taken to license mid-gray as a dark *background*. But a background must be checked
> the other way round: **text on it**. `#faf9f5` on `#b0aea5` is the same 2.11:1 pair seen on light,
> and that is the number that matters. See §Correction below.

## Correction — SAD-69 D (dark surfaces)

**Commits:** `f1caa8f` (fix) and this documentation update.

### What was wrong

`darkTheme` used `palette.midGray` (`#b0aea5`) for **both** `bgSubtle` and `bgStripe`. Body text
on dark is `palette.light` (`#faf9f5`), and `#faf9f5` on `#b0aea5` measures **2.11:1** — far below
the 4.5:1 AA floor. Every striped row in dark theme was unreadable, and so was the header.

The mistake was recorded as acceptable in the original run because the pair was measured in the
wrong direction: muted-on-dark is 8.29:1 and reads as passing, but a *background* has to be
checked as text-on-background.

### What changed

Two entries were added to `palette` in `src/ui/theme/tokens.ts`. Both are new values chosen by
Tablify; neither is part of the unverified third-party summary in `spec/branding.md`, and no
existing palette entry was touched:

| entry | hex | used for | body-text contrast |
|---|---|---|---|
| `darkSurface` | `#2a2926` | `darkTheme.bgStripe` | **13.81:1** — AA PASS |
| `darkHeader` | `#33322d` | `darkTheme.bgSubtle` | **12.19:1** — AA PASS |

Both stay a subtle step above the `#141413` background (1.44:1 and 1.64:1 against it), so the
stripe and header still read as surfaces rather than as dividers.

Two hardcoded Obsidian variables were also removed from the grid (T10): `--background-primary`
on the header, which overrode the plugin's own `--tablify-bg-subtle` in `styles.css` and made the
header follow the host Obsidian theme, and `--interactive-accent` for the selection outline,
replaced with `--tablify-selection`. See `docs/evidence/P3-09.md` for the theme-independence
requirement they violated.

### Verification

`tests/ui/contrast.test.ts` now asserts body text against `bg`, `bgSubtle` **and** `bgStripe` in
both themes, reading the real token values rather than literals — so the check cannot drift from
the theme again. `scripts/check-contrast.mjs` was updated to measure the same surfaces and to
exit non-zero if any of them fails; its old `lightGray on dark (stripe)` row described a pair the
code never used and has been removed.

### Still open

- The focus ring (`#d97757`) on the light background measures **2.96:1**, just under the 3:1
  floor of WCAG 2.1 **1.4.11** (non-text contrast). It passes on dark (5.90:1). Fixing it means
  changing an accent value, which is a branding decision (G-B1), so it is recorded here rather
  than changed. The script prints it as informational.
- Muted text on light (`#b0aea5`, 2.11:1) is still secondary-only. No UI text uses it in the new
  toolbar for that reason — the row-count badge and placeholder text use `--tablify-text`.
- Device and real-vault screenshots remain **NOT RUN** (see above).
