## Change

### 1. The phone toolbar (`styles.css`, `src/ui/faIcons.ts`, `src/views/grid/toolbar.ts`)

The prototype's toolbar buttons are plain flex items: `white-space: normal` (labels wrap to two
lines), `flex: 0 1 auto` (they shrink as far as their longest word allows). The plugin pinned them
with `white-space: nowrap; flex: 0 0 auto`, so at 390px the row kept full-width pills and 148px of
horizontal scroll: the mobile row was 332×86 against the prototype's 332×102, **Add Field 58–61 % off
and Add Row 37–41 % off**, plus 26–43 % on every region below them (card, grid, title, insert row).

The phone media block now carries one rule for it:

```css
.tablify button.tablify__toolbar-button { white-space: normal; flex: 0 1 auto; }
```

`tests/ui/toolbarMobile.test.ts` guards both halves of the decision (the phone block wraps and
shrinks; the desktop pin survives outside the block; the actions row keeps `overflow-x: auto`).

That gave dimension-identical buttons (`Add Row` 74×54, `Add Field` 77×54, `Filter` 80×38 — all 0.00 %)
but left 1.4–2 % inside the two labelled pills, and 0.5–2 % inside the icon pills. The cause turned
out to be sub-pixel icon boxes:

| Finding | Evidence |
|---|---|
| Font Awesome rounds an icon's advance to a **whole pixel**: `Math.round(viewBoxWidth / 512 × font-size)`. Measured in the prototype: `cloud-arrow-up` 640/512 × 11px = 13.75 → **14**, `plus` 448/512 × 10px = 8.75 → **9**, `grip-vertical` 320/512 × 12px = 7.5 → **8**, `sliders`/`filter` 512/512 → exact | canvas `measureText` `width` at 1–16px |
| The plugin's inlined SVGs kept the exact fraction, so a 13.75px Sync icon pulled every later pill 0.25px left (Sync 39.75, Filter x 166.75, Add Row 73.75 @ 254.75). The fraction then phase-shifted the 12px labels' glyphs | pixel-metric probe, all pills |
| Emitting `14/11em` is not enough: layout snaps 13.9997px down to the next 1/64px (13.984375) and the quarter-pixel returns | re-probe after the em fix |
| Centring the 11px ↶ ↷ glyph in the prototype's 16px text line puts it at 122.5px; the prototype's webfont lands on 122px | DOM box probe, both themes and viewports |

`faIcon(name, sizePx?)` now emits **whole-pixel** `width`/`height` when the render size is known
(`src/ui/faIcons.ts`, generated by `scripts/gen-fa-icons.mjs`, which was updated in the same commit —
`npm run check:icons` fails otherwise). The toolbar passes its `ICON_PX` map (search 12; sync, undo,
redo, sliders 11; filter, plus, columns 10), and the undo/redo rule got
`align-items: flex-start` + `margin-top: 2px` so the glyph sits on the prototype's whole pixel.

After both fixes every pill is **element-for-element identical** in the DOM probe (390×844, dark):
Sync 40.00@29.00 icon 14.00@42.00 · undo/redo 37×38 · Filter 80@167 · Add Row 74@255 · Add Field
77@337 · Options 88@422 — the same numbers the prototype reports.

### What the residual is made of

- **Glyph rasterisation, not geometry.** 600 % zooms and ink-bbox comparisons show the same shapes in
  the same boxes; only the antialiased edge pixels differ (undo shapes are indistinguishable, the
  diff mask is a hollow outline). Painter's-algorithm check on canvas: the vendored paths and the
  6.4.0 webfont outline are the same (ink boxes agree to ≤1 of 512 units for all 20 measured glyphs);
  Font Awesome's webfont is drawn as text and the plugin's as paths, and Chromium antialiases the two
  slightly differently unless the ink lands on whole pixels — which is exactly why `Filter`, `Add Row`
  and the row-number's first column are now 0.00 % and the round glyphs are 0.3–1 %.
  Removing the last of it would mean shipping the Font Awesome webfont and rendering `<i>` text
  instead of inline SVG; that is a separate, larger change (offline font asset, every icon call site,
  the `svg.tablify__fa` CSS rules) and is **not** part of this step.
- **The `Add Field` / `Options` label clip (the one deliberate deviation).** The prototype's actions
  row is 481px wide in a 332px row and does not clip at the row: its wrapped label glyphs paint past
  the card edge until the viewport cuts them. The plugin keeps `overflow-x: auto` so Add Field and
  Options stay reachable on a phone (the prototype's own mobile design cannot open Options at all),
  which clips those glyph slivers at the row edge. Half of the 1.40/1.96 % on `btn-add-field` is that
  sliver; the rest is icon antialiasing. Flagged to the owner — literal clipping is one CSS value away
  if the reachability trade-off is not wanted.
